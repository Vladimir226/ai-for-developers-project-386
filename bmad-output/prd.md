# PRD: «Запись на звонок» (Календарь звонков)

**Версия:** 1.2
**Дата:** 2026-11-07
**Статус:** Approved (источник — описание заказчика + контекст репозитория)
**Репозиторий:** https://github.com/Vladimir226/ai-for-developers-project-386.git

## Описание проекта

«Запись на звонок» — упрощённый сервис бронирования времени по мотивам Cal.com.
Базовый сценарий: владелец публикует доступные интервалы времени для встреч,
другой пользователь выбирает свободный слот и записывается на звонок.

Это учебный проект Хекслета (программа «AI for Developers»). Ценность проекта —
в процессе разработки и устройстве приложения, а не в конкурентном фичесете.

## Ограничение доставки (главное)

Приложение может быть выполнено на любом стеке технологий. Ограничение задаёт
итоговый результат: **приложение должно собираться в Docker-образ и запускаться
в контейнере**.

## Ограничения репозитория (project context)

- CI-воркфлоу `.github/workflows/hexlet-check.yml` автоматически запускается на
  каждый пуш. **Его нельзя удалять, переименовывать или редактировать.** Для
  прохождения проверки проект предоставляет Makefile-цели (`install`, `test`,
  `lint`), делегирующие в npm-скрипты.
- README.md репозитория — лицо проекта для работодателя: разделы «Установка» и
  «Использование» актуализируются по ходу разработки.
- Работа с API — контракт-фёрст (обязательная часть ТЗ): TypeSpec-контракт,
  сгенерированная OpenAPI-спецификация, клиентский SDK для фронтенда.
  Серверные типы/маршруты генерируются, если фреймворк это поддерживает; при
  отсутствии серверного генератора (наш случай — Next.js App Router) бекенд
  реализуется по контракту и проверяется тестами (ADR-010).

## Вне области действия (намеренно исключено)

- Авторизация и личные кабинеты
- Интеграции с внешними календарями
- Уведомления (email/push)
- Многопользовательская модель (несколько владельцев)

Функциональность намеренно ограничена, чтобы сосредоточиться на главном.

## Функциональные требования (FR)

| ID     | Требование                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------- |
| FR-001 | Владелец публикует доступный интервал времени (дата, начало, конец)                             |
| FR-002 | Владелец видит список опубликованных интервалов и может удалить неактуальный                    |
| FR-003 | Посетитель открывает публичную страницу бронирования и видит только свободные будущие интервалы |
| FR-004 | Посетитель выбирает свободный интервал, указывает имя и контакт, бронирует звонок               |
| FR-005 | Система исключает двойное бронирование одного и того же интервала                               |
| FR-006 | Забронированный интервал перестаёт отображаться как свободный                                   |
| FR-007 | Владелец видит список бронирований и может отменить бронь — интервал снова становится свободным |

## Нефункциональные требования (NFR)

| ID      | Категория             | Требование                                                                                                     |
| ------- | --------------------- | -------------------------------------------------------------------------------------------------------------- |
| NFR-001 | Portability           | Один Docker-образ; запуск `docker run` без внешних зависимостей; данные переживают рестарт контейнера (volume) |
| NFR-002 | Data Integrity        | Двойное бронирование невозможно в принципе, включая конкурентные запросы (гарантия на уровне БД)               |
| NFR-003 | Maintainability       | Один язык на всём стеке; явные границы модулей; стратегия тестирования определена                              |
| NFR-004 | Usability             | UI на русском языке; адаптивная вёрстка (desktop + mobile); время отображается в таймзоне владельца            |
| NFR-005 | Performance           | p95 API-ответов < 300 мс при демо-нагрузке (единственный инстанс, ≤10 rps)                                     |
| NFR-006 | Observability         | Структурированные JSON-логи с request-id на каждый HTTP-запрос                                                 |
| NFR-007 | Security (минимум)    | Валидация всех входных данных API; контейнер работает не от root; секретов в образе нет                        |
| NFR-008 | Reliability (минимум) | Endpoint здоровья `/api/health`; SQLite в WAL-режиме; корректный graceful shutdown                             |
| NFR-009 | Maintainability (CI)  | Пуш в репозиторий проходит hexlet-check CI: Makefile-цели `install`, `test`, `lint` выполнимы и зелёные        |
