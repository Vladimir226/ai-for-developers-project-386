# Вычисляемые слоты из типов событий и рабочих часов

**Status:** Accepted
**Supersedes:** ADR-0008 (дискретные слоты, UNIQUE `slot_id`)
**Drives:** шаг 5 ТЗ (`docs/hexlet-requirements.md`), решения D1–D3, D6, D12 карты #28
**Date:** 2026-11-07

**Context:** Аудит требований Хекслета (шаги 2–7, карта #28) показал главное
расхождение с реализацией: по ТЗ владелец задаёт **типы событий с
длительностью**, а слоты генерируются в **рабочие часы**; ADR-0008 же
описывал ручную публикацию дискретных интервалов. Продакшена нет, модель
можно привести к ТЗ деструктивной миграцией (D5). Решения D1–D12 карты #28 —
источник истины.

**Decision:**

- **Слоты не хранятся в БД.** Хранимые сущности — `EventType` (название
  1..100, описание ≤500, длительность в минутах 15..180) и `WorkingHours`
  (интервалы по дням недели; дефолт Пн–Пт 09:00–18:00 в зоне `APP_TZ`,
  Сб–Вс выходные; перерывов внутри дня нет; редактируются владельцем — D3).
- **Бронь = тип события + старт + контакты** гостя (имя, контакт,
  необязательный комментарий). Интервал брони — полуинтервал
  `[start, start + длительность типа)`; хранение и передача времени — UTC,
  отображение в `APP_TZ` (ADR-0009).
- **Генерация слотов:** окно записи — 14 календарных дней, начиная с
  сегодняшнего дня по `APP_TZ` (D6); старты идут внутри рабочих часов дня с
  **шагом, равным длительности выбранного типа** (D2); слот должен целиком
  помещаться в рабочие часы дня.
- **Занятость = наложение полуинтервалов броней, включая разные типы**
  (D12): интервалы двух броней не пересекаются ни для какого сочетания
  типов; частичное наложение отклоняется (60 мин в 10:00 + 30 мин в 10:30 →
  409), примыкание `[10:00,11:00)` и `[11:00,11:30)` допустимо. Гостю
  предлагаются только старты, не пересекающиеся с существующими бронями.
- **Защита от гонок** — серверная транзакция с предикатом пересечения на
  одиночном писателе SQLite (WAL — ADR-0002): проверка наложения и INSERT
  выполняются атомарно; конкурентные брони на пересекающиеся интервалы дают
  ровно один 201, остальные 409. UNIQUE `slot_id` из ADR-0008 уходит вместе
  со старой моделью.
- Удаление типа события — каскадное: его брони удаляются вместе с ним (D4).
  Переход на новую модель — деструктивная миграция со сбросом дев-данных
  (D5).

**Consequences:**

- Easier: модель соответствует ТЗ шагов 5–6; владелец управляет типами и
  рабочими часами, а не каждым интервалом вручную; правило занятости одно
  для всех типов.
- Accepted cost: список слотов вычисляется, а не читается из таблицы (при
  демо-нагрузке это дёшево: окно × часы × типы); антидубль держится на
  транзакции с предикатом, а не на констрейнте схемы — корректность
  предиката фиксируется тестами (гонки, наложение разных типов); изменение
  длительности типа не пересчитывает уже созданные брони — их интервалы
  определяются на момент создания.

**Alternatives:** материализация вычисленных слотов в таблицу на день
(лишняя сущность и синхронизация с бронями); общий шаг стартов для всех
типов (отвергнут — D2); перенос UNIQUE на вычислимый ключ интервала
(возможны коллизии на стыках разных типов).

**Revisit when:** появятся несколько владельцев, буферы между бронями или
перерывы внутри рабочего дня.
