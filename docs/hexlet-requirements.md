## Шаг 2. Каркас приложения

На этом шаге собираем каркас: бекенд, фронтенд, программу запуска тестов, линтеры и прогон проверок в GitHub Actions. Функциональности здесь пока нет — появляется рабочая основа, на которую дальше кладутся фичи.

Главный ориентир шага — официальный getting started вашего фреймворка. Открывайте документацию и идите по ней, а команды может выполнять агент. Причина такая: модель помнит прошлые версии инструментов и уверенно предлагает устаревший способ создать проект, подключить сборку или программу запуска тестов. Документация фреймворка показывает актуальный способ, и каркас, собранный по ней, потом не приходится разбирать.

Стек вы выбираете сами. Рекомендуют TypeScript и Vite, для интерфейса shadcn/ui или Mantine: с ними агенты дают более точные подсказки, а типы упрощают правки по ходу проекта. Это рекомендация, можно взять свои инструменты.

До выбора стека проверьте цепочку TypeSpec → OpenAPI → генератор SDK для языка фронтенда. Клиентский SDK обязателен. Для бекенда генерация типов, схем проверки запросов и маршрутов зависит от фреймворка. Если подходящего серверного генератора нет — реализуйте сервер по контракту и проверьте совпадение тестами.

Тестов на функциональность здесь ещё нет, поэтому в CI достаточно одного дымового теста: приложение поднимается и отвечает. Задача шага — чтобы прогон тестов и линтера работал автоматически до появления первой фичи.

Рекомендуется mise для всего окружения разработки: в `mise.toml` фиксируются версии инструментов, переменные окружения, задачи установки, запуска, сборки и проверок. Git-хуки — через hk, установленный с помощью mise. Фоновые серверы — через daemons mise (включить `experimental = true` в `[settings]`, зафиксировать версию pitchfork).

Проверки собираются в одну задачу, например `mise run check`: линтер, проверка типов (если есть в стеке) и дымовый тест. GitHub Actions вызывает эту же команду. Выбор другого инструмента допустим — команды и версии должны быть воспроизводимыми.

### Требования

- Бекенд и фронтенд запускаются локально.
- В проекте есть команды запуска тестов и линтера.
- Одна команда запускает все текущие проверки локально и в GitHub Actions на каждый push, прогон зелёный. Версии инструментов зафиксированы в проекте.
- Коммиты идут по Conventional Commits.
- В корне репозитория есть AGENTS.md с командами запуска, тестов и линтера и с правилом про формат коммитов.
- AGENTS.md короткий и без противоречивых правил. В нём только команды, устройство проекта и правила, которые из кода не читаются.

### Задачи

1. Выберите стек и создайте каркас бекенда по getting started вашего фреймворка.
2. Подключите фронтенд и убедитесь, что он собирается и открывается.
3. Выберите программу запуска тестов под свой стек, подключите её и напишите один дымовый тест запуска приложения.
4. Подключите линтеры.
5. Соберите проверки в одну команду и настройте её вызов из GitHub Actions на каждый push. Рекомендуется mise для версий, задач, хуков и фоновых процессов. Подберите инструменты по dev-guardrails и проверьте их запуск.
6. Запустите инициализацию агента (`/init`), получите AGENTS.md, сократите его до рабочего минимума и запишите правило про формат коммитов.

### Результат шага

Каркас приложения запускается локально, одна команда прогоняет проверки на вашей машине и в GitHub Actions, в репозитории есть AGENTS.md с рабочими командами.

## Шаг 3. Скиллы и агентная среда

Дальше проект идёт по одному циклу: обсудили задачу, зафиксировали спецификацию, разложили её на тикеты, реализовали. Этот цикл собран в набор скиллов, и на этом шаге мы подключаем его к репозиторию.

Скилл — переиспользуемый сценарий работы: директория с файлом SKILL.md, где записано, что делать, в каком порядке и какие проверки выполнить. Берётся набор инженерных скиллов Мэтта Покока: ставится одной командой и работает в любом совместимом агенте.

В Claude Code скилл — готовая команда через слэш (например, `/wayfinder`). В OpenCode скиллы набора командами через слэш не появляются: скилл вызывается просьбой к агенту по имени («Запусти скилл wayfinder») или ссылкой на файл `@.agents/skills/wayfinder/SKILL.md`.

После установки набор настраивается под репозиторий скиллом `setup-matt-pocock-skills`: он изучает репозиторий, задаёт вопросы и записывает ответы в `docs/agents/`. На вопрос про трекер задач выбрать GitHub Issues в репозитории проекта. Метки для разбора задач — значения по умолчанию. Словарь сохраняется в GLOSSARY.md, решения — в `docs/adr/`.

В новой сессии передавайте агенту ссылку на задачу и просите прочитать AGENTS.md и записанные решения. Например: «Запусти скилл implement-spec для спецификации #12 из этого репозитория. Сначала прочитай AGENTS.md, спецификацию, связанные тикеты и их зависимости».

### Требования

- Набор скиллов установлен и доступен в агенте.
- В репозитории есть `docs/agents/` с записанной конфигурацией трекера, меток и документов предметной области.
- В AGENTS.md появился раздел про скиллы.

### Задачи

1. Установите набор скиллов: `npx skills@latest add mattpocock/skills`. Установщик спросит, для какого агента ставить и какие скиллы брать. Выберите своего агента и не снимайте отметку со скилла setup-matt-pocock-skills.
2. Проверьте, что агент видит скиллы, включая implement-spec: они должны появиться в списке доступных.
3. Запустите скилл setup-matt-pocock-skills и ответьте на его вопросы, как описано выше.
4. Посмотрите, что скилл записал в `docs/agents/` и в AGENTS.md. Проверьте адрес трекера, пути словаря и решений.
5. Начните новую сессию и попросите агента назвать трекер и рабочую команду проверок по файлам проекта. Исправьте настройки, если ответ не совпал с вашей конфигурацией.

### Результат шага

Набор скиллов установлен и настроен под репозиторий: трекер, метки и документы предметной области зафиксированы в `docs/agents/`.

### Ссылки

- [Skills](https://skills.sh/) — каталог скиллов и CLI для установки.
- [mattpocock/skills](https://github.com/mattpocock/skills) — набор инженерных скиллов, который используется в проекте.
- [Работа с OpenCode](https://help.hexlet.io/ai/opencode) — установка, вход и выбор модели, справка Хекслета.

## Шаг 4. Первая фича: главная страница

Первую фичу берём небольшую: главную страницу приложения, которая рассказывает про сервис и ведёт на страницу записи. Смысл шага — пройти весь цикл работы целиком на задаче, где решений мало, и дальше применить его к бронированию.

Цикл начинается с разговора. Вызовите `/grill-with-docs`: агент проведёт интервью по задаче, будет задавать вопросы и спорить с ответами, а по ходу разговора начнёт складывать документы предметной области. На выходе — словарь проекта в GLOSSARY.md и принятые решения в `docs/adr/`.

Интервью несёт основную работу шага: агент про ваш проект не знает ничего. Разговор — способ передать знание один раз и оставить его в репозитории, чтобы не пересказывать в каждой новой сессии. Словарь держит единый язык: расхождение в словах стоит дорого — агент заводит вторую сущность там, где имелась в виду прежняя.

Дальше реализация: вызовите `/implement` — скилл берёт результат разговора, пишет код вместе с тестами, проходит ревью и коммитит результат. Отдельного шага под тесты нет, они появляются вместе с кодом.

### Требования

- Главная страница открывается и ведёт на страницу записи. До реализации бронирования на следующем этапе допустима заглушка этой страницы.
- Есть тесты на главную страницу, прогон в GitHub Actions зелёный.
- В репозитории есть GLOSSARY.md со словарём проекта.
- Принятые решения записаны в `docs/adr/`.

### Задачи

1. Передайте агенту сценарий и ограничения из введения, вызовите `/grill-with-docs` и пройдите интервью по главной странице.
2. Проверьте, что в GLOSSARY.md появился словарь проекта, а в `docs/adr/` — принятые решения.
3. Вызовите `/implement` и реализуйте страницу вместе с тестами.
4. Убедитесь, что прогон в GitHub Actions зелёный.

### Результат шага

Главная страница работает и покрыта тестами, в репозитории появились словарь проекта и записанные решения.

### Ссылки

- [Architecture Decision Records](https://adr.github.io/) — формат записи принятых решений.

## Шаг 5. Проектирование бронирования

Основная функциональность проекта — запись на звонок: типы встреч, календарь свободных слотов, бронирование и список встреч владельца. Работы здесь на несколько сессий, и большинство решений ещё не принято, поэтому проектируем её картой решений.

Начните с `/wayfinder`. Скилл заводит в трекере карту: одну задачу, к которой прицеплены дочерние задачи. Каждая такая задача — вопрос, ответ на который надо принять до реализации: какие сущности есть в контракте, как устроена модель слотов, что происходит при конфликте между разными типами встреч, на каких границах проверять приложение тестами. Карта разбирается по одной задаче за сессию, и несколько заходов — нормальный ход работы.

Пункт назначения карты должен вести к согласованной спецификации приложения, по которой можно создавать тикеты.

### Design First и контракт

Этот шаг готовит спецификацию и тикеты. Генерацию контракта и SDK настраивает первый тикет следующего шага «Реализация».

Приложение делается в подходе Design First: сначала фиксируем поведение системы и API-контракт, потом реализуем фронтенд и бекенд по нему раздельно. Контракт задаёт границу между частями приложения и остаётся единым источником правды. Для агентов это даёт выигрыш: имея явную спецификацию, они не разбирают внутреннюю реализацию соседней части приложения, и расход токенов падает.

Контракт описывается в TypeSpec, а OpenAPI-спецификация из него генерируется. Пример описания типа события и эндпоинта:

```tsp
import "@typespec/http";

using TypeSpec.Http;

model EventType {
  id: string;
  title: string;
  durationMinutes: int32;
}

@route("/event-types")
interface EventTypes {
  @get list(): EventType[];
}
```

После генерации в OpenAPI появляется описание маршрута и модели:

```yaml
paths:
  /event-types:
    get:
      operationId: EventTypes_list
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/EventType'
components:
  schemas:
    EventType:
      type: object
      required: [id, title, durationMinutes]
      properties:
        id: {type: string}
        title: {type: string}
        durationMinutes: {type: integer, format: int32}
```

Из спецификации генерируется клиентский SDK для фронтенда: типы запросов и ответов вместе с функциями вызова эндпоинтов. На бекенде из той же спецификации генерируются свои артефакты (типы, схемы проверки запросов и заготовки маршрутов), если для фреймворка есть генератор; если нет — серверную часть пишут по контракту, а совпадение проверяют тесты.

```text
TypeSpec ──> OpenAPI ──┬──> клиентский SDK (фронтенд)
                       └──> серверные артефакты (если есть генератор)
```

Генерация не доказывает, что фронтенд использует клиент и что сервер возвращает описанные ответы — эти свойства проверяются отдельно на следующем шаге. Команды генерации хранятся в Makefile или в скриптах пакета, чтобы цепочка повторялась одним вызовом.

### Что должно уметь приложение

В проекте две условные роли: владелец календаря и гости. Регистрации и авторизации нет. Владелец календаря — один заранее заданный профиль, который по умолчанию используется в админской части. Гость бронирует слоты без создания аккаунта и без входа в систему.

Владелец календаря может:

- Создавать типы событий: id, название, описание и длительность в минутах.
- Просматривать страницу предстоящих встреч, где в одном списке показаны бронирования всех типов событий.

Гость:

- Может посмотреть страницу с видами брони, где доступно название, описание и длительность.
- Выбирает тип события, открывает календарь и выбирает свободный слот в ближайшие 14 дней.
- Создаёт бронирование на выбранный слот.

Правило занятости:

- Интервалы двух записей не пересекаются, даже для разных типов событий и одновременных запросов. После брони с 10:00 до 11:00 запись с 10:30 до 11:00 отклоняется. Запись с 11:00 допустима.
- Если гость пытается занять уже занятое время, он видит понятное сообщение о конфликте.

Окно записи по умолчанию:

- Окно записи сдвигается с текущей датой и занимает 14 календарных дней. С какого дня оно начинается, с сегодняшнего или с завтрашнего, — решить самим и записать в спецификацию.
- Слоты формируются в рабочие часы владельца, например с 09:00 до 18:00. Часы работы и часовой пояс, в котором они заданы, записываются в спецификацию.
- Слот длится столько, сколько выбранный тип события. Шаг доступных стартов записывается в спецификации: может совпадать с длительностью типа или быть общим для всех типов.
- Гость может записаться только на свободный слот из этого окна.

Внутреннюю реализацию, стек и структуру проекта выбираете сами. Здесь договариваются о внешнем поведении системы: какие сценарии поддерживаются, какие данные передаются и какие ограничения действуют при бронировании.

### Спецификация и тикеты

Когда решения по карте приняты, соберите их в спецификацию: вызовите `/to-spec`. Скилл интервью не проводит — он синтезирует спецификацию из того, что уже обсуждено, поэтому запускать его надо в сессии, где карта и ответы по её задачам загружены в контекст. Спецификация публикуется в трекер и содержит пользовательские истории, принятые решения по реализации и решения по тестированию.

Дальше разложите спецификацию на тикеты: `/to-tickets`. Тикеты вертикальные: каждый проходит через все слои приложения (контракт, сервер, интерфейс, тесты) и проверяется по отдельности. Каждый тикет объявляет, какие тикеты его блокируют.

Первый тикет реализации должен проверить всю контрактную цепочку на небольшой функции (например, получение списка типов встреч: TypeSpec → OpenAPI → сгенерированный SDK → сервер → отображение на странице). В тикете записываются команды генерации и проверка ответа API.

В спецификацию и тикеты включаются: общая команда проверок, API-тесты, браузерный сценарий, проверка одного теста с временно нарушенным правилом бронирования и настройка release-please после первой функции.

### Требования

- В трекере есть карта решений, её вопросы закрыты с записанными ответами.
- В спецификации описаны роли владельца и гостя, типы встреч, окно 14 дней, рабочие часы, часовой пояс, длительности, шаг стартов, примыкание и конфликты интервалов.
- Спецификация задаёт API и ожидаемые ответы, включая создание бронирования, ошибки данных и конфликт занятого времени. Пути, методы и поля выбираются сами.
- Названы границы тестирования, включая прямые запросы к API и браузерный сценарий с настоящим сервером.
- В трекере есть тикеты с зависимостями и ссылками на спецификацию. Первый тикет проводит одну небольшую функцию через контракт, генерацию, сервер, интерфейс и тесты.

### Задачи

1. Вызовите `/wayfinder` и заведите карту решений для согласованной спецификации приложения.

## Шаг 6. Реализация

Спецификация и тикеты готовы. Вызовите `/implement-spec` и передайте ссылку на спецификацию в GitHub Issues. Попросите прочитать AGENTS.md, связанные тикеты и их зависимости. Скилл берёт в работу всю спецификацию и собирает реализацию в одной общей ветке.

Тикеты образуют граф зависимостей. Скилл сам выбирает готовые к работе тикеты, запускает исполнителей в отдельных рабочих копиях и объединяет результаты в общей ветке. Независимые задачи могут выполняться параллельно. Настройка контрактной цепочки предшествует задачам, которые её используют.

Исполнители пишут код через цикл TDD и проверяют границы, заданные спецификацией. После выполнения тикетов `/implement-spec` запускает общее ревью ветки и исправляет его замечания. Если работа сдаётся через pull request, скилл готовит его к ревью.

Основной сценарий бронирования проверяется в браузере: гость выбирает тип встречи, открывает календарь, занимает свободный слот и видит подтверждение, а владелец видит эту встречу в своём списке. Сценарий закрепляется браузерным тестом в репозитории (рекомендуется Playwright).

Правила бронирования должны выполняться на сервере. Проверка занятости только в интерфейсе обходится любым другим клиентом: прямой запрос в API создаст вторую запись на то же время.

Обращения к API идут через сгенерированный клиентский SDK. Если контракт меняется, порядок такой: правка TypeSpec → генерация → код обеих сторон.

Коммит реализации ссылается на тикет, который он закрывает, например `feat: запись на свободный слот (#12)`. До вызова `/implement-spec` записать это правило в AGENTS.md рядом с правилом про формат коммитов.

### Контрактная цепочка и проверки

- Проверьте результат первого тикета: операция описана в TypeSpec, OpenAPI и клиентский SDK сгенерированы, страница обращается к серверу через клиент. Если фреймворк поддерживает серверный генератор — добавлены его артефакты. Команды всей генерации объединены в один вызов.
- В AGENTS.md должны быть названы генерируемые пути и записан запрет править их руками. Если артефакты коммитятся — CI повторяет генерацию и проверяет изменения, включая новые файлы. Если не коммитятся — CI генерирует их из чистого состояния перед сборкой и тестами.
- Общая команда проверок запускает линтер, проверку типов, API-тесты и браузерный тест. Браузерный тест работает с запущенным приложением, без подмены ответов API бронирования.

### Проверка теста

В одном из тикетов агент проверяет чувствительность теста к ошибке: в отдельной рабочей копии временно нарушает запрет частичного пересечения разных типов встреч и запускает защищающий тест. Тест должен упасть; если остаётся зелёным — агент дополняет тест, затем восстанавливает правильную реализацию. Сломанная версия сервиса не публикуется. В тикете сохраняются: название правила, команда, результаты красного и зелёного запусков и короткое объяснение причины падения.

Настройка release-please входит в граф тикетов и выполняется после первой функции: отдельный workflow использует Conventional Commits для подготовки release-PR. Проверьте, что после изменения основной ветки workflow создаёт release-PR.

### Требования

- Сквозной сценарий гостя проходится целиком: выбор типа встречи, календарь, запись на свободный слот, подтверждение.
- Одна команда из AGENTS.md запускает все проверки локально и в CI, включая браузерный сценарий с настоящим сервером без подмены ответов API бронирования.
- Занятый слот не предлагается как свободный, повторная запись на это время не проходит, в том числе для другого типа встречи.
- При конфликте слота гость видит понятное сообщение.
- Правила бронирования выполняются на сервере.
- Есть страница владельца со списком предстоящих встреч всех типов.
- В репозитории есть TypeSpec-контракт, OpenAPI и клиентский SDK генерируются одной командой. Серверные артефакты генерируются, если для фреймворка есть подходящий генератор.
- Реализация совпадает с контрактом по путям, методам, полям, успешным ответам и ошибкам данных и конфликта. API-тесты проверяют эти ответы.
- Генерация повторяется в CI. Генерируемые пути и запрет ручных изменений записаны в AGENTS.md.
- Фронтенд обращается к API через сгенерированный клиентский SDK.
- Тесты покрывают основной сценарий бронирования и конфликт слотов, прогон в GitHub Actions зелёный.
- Тест на конфликт проверяет и частичное наложение встреч разной длительности, например встречу на 60 минут в 10:00 и встречу на 30 минут в 10:30.
- Коммиты реализации ссылаются на тикеты, правило записано в AGENTS.md.
- Тикеты спецификации выполнены через `/implement-spec`, результаты собраны в одной ветке и прошли общее ревью.
- В тикете есть результат проверки одного теста с временно нарушенным правилом и после восстановления.
- release-please подключён и создаёт release-PR.

### Задачи

1. Допишите в AGENTS.md правило, что коммит ссылается на тикет.
2. Вызовите `/implement-spec` со ссылкой на спецификацию и связанные тикеты. Следите за ходом реализации и отвечайте на вопросы агента.
3. Проверьте итоговую ветку или pull request, включая контрактную цепочку, общий прогон проверок, браузерный сценарий и результаты эксперимента с тестом.
4. Передайте замечания агенту, получите исправления и убедитесь, что GitHub Actions зелёный. После ревью внесите результат общей ветки в основную и проверьте появление release-PR.

### Результат шага

Приложение работает по контракту, основной сценарий бронирования проходится и покрыт тестами, включая браузерный.

### Ссылки

- [release-please](https://github.com/googleapis/release-please) — подготавливает релизы по Conventional Commits.
- [release-please-action](https://github.com/googleapis/release-please-action) — запускает release-please в GitHub Actions.

- [Chrome Devtools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) — диагностика проблем в браузере, включая сеть, консоль и состояние страницы.

## Шаг 7. Docker и деплой

На этом шаге приложение готовится к запуску в продакшене с помощью Docker: образ одинаково запускается локально, в CI и в облаке.

Деплой отдаётся агенту. У хостингов есть MCP-серверы, через которые агент создаёт сервис, выкатывает образ и проверяет, что приложение отвечает. Конфигурация MCP хранится в проектном файле агента (OpenCode — `opencode.json`, Codex — `.codex/config.toml`) или в безопасном шаблоне с инструкцией подключения. При входе по OAuth опишите процедуру, данные сессии в Git не добавляются. API-ключ можно получать из переменной окружения. Файлы с реальными ключами исключить из Git, шаблон оставить в репозитории.

По итогам шага — Docker-образ, при запуске которого приложение автоматически стартует внутри контейнера, и публичная ссылка на работающий сервис.

### Требования

- В корне репозитория должен лежать файл Dockerfile. По нему в проверке собирается образ и запускается приложение.
- При запуске контейнера из собранного образа приложение должно стартовать автоматически.
- Приложение должно запускаться в контейнере по порту из переменной окружения PORT. Эта переменная используется и при деплое, и в автоматической проверке проекта.
- После деплоя у приложения должна быть публичная ссылка, и она добавлена в репозиторий.
- В репозитории есть проектная конфигурация MCP выбранного агента или безопасный шаблон с инструкцией. Вход через OAuth и переменные окружения допустимы.
- По публичной ссылке проходит сценарий гостя и владельца, включая отказ повторного бронирования. В README.md описано, сбрасываются ли данные после перезапуска.
- В истории репозитория нет ключей, токенов и других секретов.

### Задачи

1. Соберите Docker-образ приложения.
2. Подключите MCP-сервер хостинга в конфигурации проекта и настройте деплой с запуском приложения по PORT. Проверьте работу приложения. Если с Render возникли проблемы (требует оплату, недоступен и так далее) — задеплойте на Railway: тот же Docker-образ, запуск по PORT и публичная ссылка. Для проверки платформа не важна, важно, чтобы приложение было опубликовано и работало по PORT.
3. По публичной ссылке создайте запись, проверьте её в списке владельца и убедитесь, что пересекающаяся запись отклоняется.
4. Добавьте в README.md ссылку, порядок подключения MCP без секретов и ограничение хранения данных.

### После приёмки

Перед началом продолжения проекта перенесите принятые исправления в исходную версию второго проекта. Не заменяйте его файлы целиком, если там уже есть новые изменения. В README.md продолжения укажите, от какой версии первого проекта начали работу. Начинать второй проект ради сдачи первого не требуется.

### Результат шага

Есть Dockerfile для сборки образа, приложение запускается в контейнере по PORT и доступно по публичной ссылке.
